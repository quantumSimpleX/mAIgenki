# pB05-T02 — oauthRoute

**Part:** B, **Phase:** 5. **Implements:** lmfPlan.md A9 step 8 (completion route, ~line 228).

## Description
Create **`src/app/oauth/openrouter.tsx`** — the OAuth completion route (Expo Router screen, **default export**):
- **Web**: render "Completing sign-in…" and call `WebBrowser.maybeCompleteAuthSession()` to close the popup and hand the result back.
- **Native cold-launch path**: read `code` via `useLocalSearchParams`, load the persisted verifier from `ConfigStore` (`lmf_oauth_pending`), complete the exchange, then delete the pending verifier. Navigate back to the app on success/failure.
- Reuse `connectOpenRouter`/exchange logic from `oauth.ts` (don't duplicate the exchange).

Verify SDK 56 expo-router + expo-web-browser `maybeCompleteAuthSession` usage.

## Dependencies

## Acceptance criteria

- Web calls `maybeCompleteAuthSession()`; native cold-launch reads code + persisted verifier and completes exchange.

## Implementation Notes

Created `src/app/oauth/openrouter.tsx` as a default-export Expo Router screen with two independent effects:

- **Web** (`Platform.OS === 'web'`): one `useEffect` calls `WebBrowser.maybeCompleteAuthSession()` unconditionally. The actual key exchange already happened (or is in flight) in the opener window's in-memory `connectOpenRouter`/`openAuthSessionAsync` call — this screen's only job on web is to hand the result back and let the popup close. It never touches `db`.
- **Native cold-launch**: a second `useEffect` (guarded to skip on web, and to wait until `useOptionalDatabase()` resolves non-null) reads `code` via `useLocalSearchParams<{ code?: string }>()`, loads the verifier via `getPendingVerifier(db)`, and calls `completeOAuthExchange(db, code, verifier)` — reusing pB05-T01's logic verbatim, no duplicated PKCE/exchange code.
- Renders a single centered status `<Text>` ("Completing sign-in…" → success/error message) on both platforms; after the native path settles, it waits 1.2s (`REDIRECT_DELAY_MS`) so the message is readable, then `router.replace('/')`. Missing `code` or an expired/missing verifier are treated as terminal error states with their own message, without calling `completeOAuthExchange`.
- Obtained `db` via the existing `useOptionalDatabase()` context (`@/lib/db/provider`), the same pattern used by `analyzing.tsx`, `bodymap.tsx`, and `ProviderSettings.tsx` — no new plumbing introduced.

**Rework (QA round 2 — Issue 1 fix):** QA flagged that the pending OAuth verifier was never deleted after a native cold-launch exchange, since `completeOAuthExchange` has no side effect on `lmf_oauth_pending` and the only cleanup (`clearPendingVerifier`) was private to `oauth.ts`, reachable only from `connectOpenRouter`. Fixed exactly per QA's recommendation:
- `src/lib/llm/oauth.ts`: added `export` to `clearPendingVerifier` (no signature/behavior change).
- `src/app/oauth/openrouter.tsx`: `finish()` now calls `await clearPendingVerifier(db!)` once, right before the redirect `setTimeout`, on **every** terminal outcome of the native path — success, exchange failure, missing code, and missing/expired verifier — mirroring `connectOpenRouter`'s own "clear on every terminal outcome" pattern. This is a single call site covering all branches rather than one call per branch, so there's no risk of a branch being missed if a new outcome is added later. Web path untouched — it never reads/writes `lmf_oauth_pending`.

## Issues Found

**Issue 1 — Pending OAuth verifier is never deleted after a successful native cold-launch exchange (Medium, should block DONE)**

- **Severity**: Medium. Not a security/financial-impact bug (a PKCE code verifier is useless without its matching single-use authorization code, and OpenRouter's `code` is consumed by the exchange call regardless of outcome — so this is not a live-credential leak), but it is a clear, unambiguous violation of a written, testable acceptance criterion.
- **Impact**: Any user who completes OpenRouter OAuth via the **native cold-launch path** (app was killed/backgrounded during the browser redirect, so the deep link reopens the app fresh) will have the `lmf_oauth_pending` SQLite settings row left in place indefinitely after a successful sign-in, until they happen to run a full `connectOpenRouter()` flow again (which unconditionally overwrites the key via `upsertSetting` before opening a new browser session — confirmed in `src/lib/llm/oauth.ts:85`). Verified no other code path reads `lmf_oauth_pending`/`getPendingVerifier` as an absence-implies-something signal (`ProviderSettings.tsx` has no reference to it at all) — so today this does not cause any *observable* incorrect behavior, matching the dev's "functionally harmless" claim for the current codebase. But it is stale-data-in-SQLite left indefinitely, and it fails the card's own written acceptance text.
- **Likelihood**: Triggered on every successful native cold-launch OAuth connect — not a rare edge case, it's the primary purpose of this route.
- **Repro / Evidence**: Both the card's own Description ("...complete the exchange, then delete the pending verifier...") and `lmfPlan.md` A9 step 8 ("...deleted after") and A9's Phase 5 bullet ("...deleted on completion/cancel") explicitly require deletion after the native completion route finishes. `src/app/oauth/openrouter.tsx`'s `finish()` (lines 47-66) calls `completeOAuthExchange(db!, code, verifier)` on success/failure but never calls anything that deletes the `lmf_oauth_pending` row. Confirmed independently by reading `src/lib/llm/oauth.ts` in full: `completeOAuthExchange` (lines 42-63) has no side effect on the setting; only the private, unexported `clearPendingVerifier` (lines 33-35) does, and it is only called from within `connectOpenRouter` itself (lines 91, 103, 107, 112) — never reachable from the new route since it isn't exported. The dev's self-report in Implementation Notes accurately describes this.
- **Coverage gap**: `__tests__/app/oauthRoute.test.tsx` does not assert anything about `lmf_oauth_pending`/verifier deletion in any of its 5 cases — the mock for `@/lib/llm/oauth` only stubs `getPendingVerifier`/`completeOAuthExchange`, with no assertion that a cleanup call happens or doesn't. So this gap would not be caught by the existing regression net, and a future accidental duplication of cleanup logic (double-delete, wrong key, etc.) also wouldn't be caught.
- **Recommendation**: Export `clearPendingVerifier` from `src/lib/llm/oauth.ts` (or add a thin public wrapper) and call it from the route's `finish()` after `completeOAuthExchange` resolves (both success and failure branches — mirroring `connectOpenRouter`'s own pattern, which clears on every terminal outcome, not just success). This is a small, contained fix scoped to the two files this task already owns plus one export added to `oauth.ts`. Add one test asserting the cleanup call happens after a completed exchange. Recommend sending back to CODE for this fix rather than accepting as-is — the acceptance criteria and lmfPlan.md are explicit and unambiguous on this point, and the fix is low-risk and small.

No other issues found. Web/native platform branching, `useOptionalDatabase()` usage, error-state handling, and the test suite's mock structure are all sound.
