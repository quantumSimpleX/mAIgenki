## Implementation Record

### 2026-07-31 — DevAgent, Tasks 4.1–4.4

**Task 4.1.** `renderPageToCanvas(uri, pageNumber)` is exported alongside `renderPageToBlob` (the card's literal signature) even though only the latter is named in `userDataTask.md`. Reason: `compressToTarget` (Task 4.2) takes an `HTMLCanvasElement`, not a `Blob` — if `renderPageToBlob` were the only export, Task 4.3's pipeline wiring would have to either re-render the PDF page a second time just to get a canvas for compression (wasteful — a full `pdfjs-dist` render pass per page, twice), or `compressToTarget` would need a different signature than the card specifies. Splitting the canvas-producing step out (used directly by `pipeline.ts`) from the blob-encoding step (kept for `renderPageToBlob`'s own literal contract) avoids that double-render without changing either function's documented signature. `page.render()` is called with `{ canvas, canvasContext, viewport }` rather than the card's `{ canvasContext, viewport }` — this repo's installed `pdfjs-dist` (^6.1.200) requires `canvas` in `RenderParameters` (verified against `node_modules/pdfjs-dist/types/src/display/api.d.ts`, not guessed); `canvasContext` is also passed for backwards-compat per that same type's doc comment.

**Task 4.2.** `compressToTarget` targets `image/jpeg` (quality is meaningless for PNG, and JPEG is appropriate for photographic content like X-rays/scans). Quality steps `[0.8, 0.6, 0.4, 0.2]` tried first (cheap — no re-render), then up to 3 downscale-and-retry rounds (halving resolution each time) if quality alone can't hit the target. Per Task 0.1's documented Jest gap, the downscale path (`document.createElement('canvas')`) can't run under this project's real Jest environment; `tests/lib/compress.test.ts` stubs `document.createElement` with a fake canvas object to exercise the loop's *control flow* (call counts, ordering, bounding, fallback-instead-of-throw) as pure logic — this proves the loop terminates and behaves correctly, not that real canvas rendering/downscaling works, which remains Task 4.4's gap.

**Task 4.3.** The core design problem: Phase 3's `enrichFromText` return type (`EnrichmentResult`) had no way to tell `pipeline.ts` which sections were `imageWorthy` or their resolved page ranges — that data existed only transiently inside `enrichFromText`'s internal `structure`/`chunks` variables, never returned. Fixing this required the scope-expansion to `enrich.ts`/`chunk.ts` documented above (`TextChunk.imageWorthy`, `EnrichmentResult.imageSections`). The second design problem: linking a captured image to "whichever condition(s) that section's chunk extraction associated with it" (the card's own wording) requires a stable identifier that survives Phase 3's cross-chunk merge (`mergeConditions`) without losing origin information — solved by exporting the existing (previously private) `conditionKey()` function and having each `imageSections` entry carry the `conditionKeys` of that chunk's own pre-merge condition list; since merging never changes what `conditionKey()` returns for a given name/organ/location, `pipeline.ts` can re-derive the same key from the final persisted conditions and match by string equality without `enrich.ts` needing to track object identity across the merge. Third: `condition_records.condition_id` needs an id that matches what's actually stored — solved by assigning `c.id = c.id ?? uuid()` to every LLM-extracted condition *before* calling `persistEnrichmentResult` (which already reuses a given `c.id` verbatim, so no persistence-layer change was needed), then running image capture *after* persistence completes (so `result.recordId` is also known). Inferred conditions (from `applyInferenceRules`) are deliberately excluded from image-linking — they're synthetic, never originate from a chunk, and can't legitimately match any `conditionKeys` value. `MAX_IMAGE_BYTES = 500_000` (500KB) chosen from the acceptance criteria's "hundreds of KB, not multi-MB" wording; no other constant was specified in the card or task doc.

No real browser was available in this session; Task 0.1 already established Jest cannot substitute for one here (no `document`/`HTMLCanvasElement`, `pdfjs-dist`'s `.mjs`-only build fails under this project's Jest transform). This is a genuine, expected verification gap for this phase, not an oversight — flagged in Blockers below and left for a human or Playwright pass.

## Defects and Retests

**Finding 1 — Severity: Low. No outer try/catch around the `captureRecordImages` call site itself.**
**Impact:** If anything throws synchronously between entering `captureRecordImages` and the first per-page `try` (e.g., `matchedConditionIds` computation, or a malformed `imageSections` entry with `pageStart`/`pageEnd` as non-numbers causing a bad loop), the exception would propagate up through `processHealthRecord` and fail the entire record — contradicting the card's own acceptance criteria ("A rendering/compression failure for one page doesn't fail the whole record") in spirit, even though the currently-shipped code paths that could throw there are simple, type-safe array operations very unlikely to fail in practice.
**Likelihood:** Low today (no realistic input currently reaches that gap given `ImageWorthySection`'s TypeScript shape and `enrich.ts` only ever populating `pageStart`/`pageEnd` from an already-null-checked chunk), but a future edit to `captureRecordImages`'s pre-loop setup could reintroduce this silently since nothing currently guards it.
**Repro/Evidence:** `src/lib/pipeline.ts` lines 384-389 — the call to `captureRecordImages` is a bare `await`, not wrapped in try/catch; only the *inner* per-page loop (lines 127-171) is defensive.
**Recommendation:** Wrap the `captureRecordImages` call site itself (or the whole function body) in a top-level try/catch that traces `'image-capture-step-failed'` and swallows, as cheap insurance matching the card's stated intent literally, not just for the cases DevAgent anticipated. Small, additive, no test rewrite needed beyond one new case. Does not block this card's approval — recommend as a fast follow, not a blocking retest.
