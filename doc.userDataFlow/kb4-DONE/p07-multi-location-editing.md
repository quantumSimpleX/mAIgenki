- **P7-05 (Add mode) CONFIRMED, one non-blocking edge case found.** Read `handleLocationAdd` (bodymap.tsx ~2154) directly: reads `getConditionLocations(idb, condition.id)` — if empty, calls `updateConditionPositionLocally` (local state) + `updateIndexedConditionPosition` (the pre-existing dual-write helper, confirmed by reading its body at indexedDb.ts:351-369: it creates a deterministic `${conditionId}-primary` location row with `is_primary: true` and updates the condition's own `cx`/`cy`) + `refreshConditions()`; if non-empty, calls `putIndexedConditionLocation` with a fresh `uuid()` and `is_primary: false`.   - **Edge case (not a blocking defect):** `handleLocationAdd`'s "zero real rows" check (`getConditionLocations` read) is not atomic with the write that follows. Two Add-mode taps landing on the same legacy/fallback condition close enough together that the second tap's `getConditionLocations` read resolves before the first tap's `updateIndexedConditionPosition` write commits would both take the "zero rows" branch — since `updateIndexedConditionPosition` writes a **deterministic** id (`${conditionId}-primary`), the second write would silently overwrite the first instead of creating a second, distinct location, losing one of the two taps. Severity: **Low**. Likelihood: **Low** — requires two taps within roughly one IndexedDB round-trip of each other on a condition's *very first* Add (a one-time state per condition; subsequent taps use `uuid()` and can't collide). Impact: one lost location placement, silently — no crash, no wrong data, user can just tap again and would only lose the race a second time by more bad luck. Not a regression in this app's stated risk profile (no financial/security data). Recommend a follow-up ticket, not a merge blocker: dedupe via a single transaction or an optimistic-lock check inside `handleLocationAdd`, or simply disable the tap surface for the duration of the in-flight write.
