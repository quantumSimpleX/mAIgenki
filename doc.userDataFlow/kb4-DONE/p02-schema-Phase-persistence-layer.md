1. **Provider/facility/care-event persistence has no IndexedDB store.** `persistEnrichmentResult` accepts `providers` but doesn't write it anywhere (no `facilities`/`providers`/`condition_providers`/`provider_affiliations`/`condition_care_events` object stores exist in `indexedDb.ts`'s schema). This affects real (non-demo) uploads only — a condition's plain-text `evidence` field (e.g. "Dr. X · Hospital · City") is unaffected and still persists correctly for both demo and real data. **Recommend a new task** (not currently in `userDataTask.md` Phase 2–6) to design and add these stores before this is considered production-complete for real uploads.
2. **Blob byte-fidelity through a live IndexedDB read cannot be proven in this project's Jest environment.** Confirmed via `tests/lib/_spike02-indexeddb-blob.test.ts` (already on this branch, from the p00 spike): `fake-indexeddb` clones every stored value with Node's `structuredClone()`, which silently fails to clone a `Blob` under this project's `testEnvironment` (VM-context isolation) — a `Blob` written via `put()` reads back as `{}`, not a `Blob`, even before any of this card's export/import code runs. I initially assumed (per an earlier coordinator note) that the JSON export/import path was immune to this because it converts `Blob` → base64 before `JSON.stringify` — but empirically, `buildIndexedDbBackup`'s own `getAll()` read (the first step of `exportIndexedDbBackupToJson`) already returns the corrupted `{}` in this environment, so the encode step never sees a real `Blob` to encode. **This is not a code defect** — `putRecordImage`/`getRecordImageBlob`/`exportIndexedDbBackupToJson`/`importIndexedDbBackupFromJson` are correct and will work in a real browser (confirmed by `tests/lib/blob.test.ts`'s pure base64 round-trip, which doesn't touch IndexedDB and passes). `tests/lib/indexedDbBackup.test.ts`'s new test therefore only asserts non-Blob field fidelity through the export/import path; **full Blob byte-fidelity through a live IndexedDB store needs a real-browser manual or Playwright check**, not a Jest assertion — recommend this as an explicit item in Task 6.3's export/import round-trip verification (real data) rather than something QA should expect to see proven here.
3. **`src/app/bodymap.tsx`'s Settings backup Export/Import buttons still target the legacy SQLite path** (`@/lib/db/backup`'s `exportBackupToFile`/`pickAndReadBackup`/`restoreBackup`), not `indexedDbBackup.ts`. After this cutover, health data (conditions/measurements/locations) lives in IndexedDB, so this backup feature will export/import an increasingly empty/stale snapshot of SQLite health tables while the real data sits in IndexedDB, inaccessible to it. This was deliberately left alone this session — wiring it to `indexedDbBackup.ts` would mean redesigning this UI's data-flow (not just its data source) and risks exactly the kind of UI change the user explicitly asked not to touch without care ("please do not change UI working took long time to get right"). **Recommend a follow-up task** scoped specifically to this (likely alongside Task 6.3).
4. **LLM provider profile/model-chain/OAuth subsystem (`src/lib/llm/profile.ts`, `client.ts`, `oauth.ts`, `refresh.ts`) intentionally remains on SQLite.** This is `doc.lmFallbackBuild/lmfPlan.md`'s subsystem, never scoped into `userDataTask.md`'s Phase 2–6. `src/lib/pipeline.ts`'s `PipelineOptions.db: SQLiteDatabase` is kept specifically to keep this subsystem working unchanged. Not a blocker, but worth recording so a future agent doesn't assume `db` is dead weight and remove it.
